# CVMaster 开发宪法

## 产品目标

CVMaster 帮求职者以尽可能低的录入成本，持续积累可验证的经历证据，并针对具体职位生成准确、可编辑的 LaTeX 简历。真实性和可追溯性优先于文案润色。

## 角色与协作

- Codex 负责产品边界、交互与系统设计、开发文档、重要技术决策和代码审阅。
- Workbuddy 负责按已批准的 PRD、数据契约和 checkpoint 落地代码；遇到需求冲突、安全边界或数据迁移问题，先停在可审阅的小 diff 并报告。
- 前端实现必须先阅读并遵循 `UI.md`；PRD、TECHSTACK、DATABASE、ROADMAP 是当前工作基线。实现若需改变这些约定，先更新对应文档并说明理由。
- 每个 checkpoint 交付可运行、可演示的纵向切片；不要以一次性大改代替可 review 的步骤。
- Workbuddy 完成一组改动后，创建 Git commit，并直接把短 commit SHA（例如 `07ccef`）发给用户。用户会把 SHA 转交给 Codex 做代码审阅；不要只发“已完成”而遗漏 SHA。提交信息应说明改动目的，提交内容不得包含密钥或本地环境文件。
- CP1 的素材输入仅在浏览器内存中做演示，界面必须持续标注 `Preview only — not saved`；不得上传、持久化或调用 AI。

## 产品不变量

1. 新增素材只要求用户提供手头已有的证据；不强迫先填写分类表单。
2. AI 提取出的事实必须保留来源引用，并标记为待确认、已确认或缺失。AI 的推断不能伪装成用户确认的事实。
3. 简历内容不得补造数字、职责、技术、成果或日期。证据不足时保留明确缺口，交由用户补充。
4. 用户数据按账户隔离。每个用户数据表都必须有明确的访问策略；服务端高权限凭证不得进入浏览器包。
5. BYOK 密钥只由服务端读取和使用；不写入日志、埋点、错误消息、客户端响应或版本库。密钥的持久化/加密策略需在对应实现 checkpoint 前完成安全审阅。
6. 上传素材、提取结果、生成简历均支持用户查看、修正和删除；删除流程要覆盖关联文件与派生数据。
7. MVP 只交付电脑端网页；桌面交互和 `prefers-reduced-motion` 必须完整，移动端布局与触控适配属于后续版本。

## 工程约定

- 面向用户的产品 UI 使用简洁英文文案；设计/产品文档可以使用中文。
- 保留原型的深空视觉方向，并按 `UI.md` 实现真正可交互的 3D 粒子星图；生产功能不依赖原型中的模拟 AI、内存数据或浏览器全局 API。
- AI 输入输出采用有版本的结构化 schema；服务端验证模型输出，保存模型/提示词版本和来源关系，不把原始模型文本当作可信数据库记录。
- 数据库 schema 的改动通过可审阅迁移完成；必须同时考虑 RLS、索引、外键、删除行为及迁移回滚/前向修复。
- 不在客户端直接抓取任意 URL。链接导入要经过服务端校验、网络访问限制和内容大小/类型限制，避免 SSRF 与恶意内容。
- 不将个人资料、简历、原始素材、API key 或模型输出写入一般应用日志。
- 改动完成后清楚说明变更范围、手动验收路径、尚存风险。除非用户要求，不主动扩张到无关功能。

## 交付审阅清单

- 关键路径是否能在电脑端完成？移动端适配不作为 MVP 验收项。
- AI 产出的每条简历事实是否能追溯到用户证据或用户补充？
- 未授权用户能否读写另一账户的数据或文件？
- API key、服务端密钥、上传文件是否可能进入客户端、日志或错误响应？
- 删除、重试、空状态、加载状态和失败恢复是否定义清楚？
- 视觉动效是否克制，并支持减少动态效果？
